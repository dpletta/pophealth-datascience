2  Project Environments for R and Python

2.1 Overview

NoteThe task: give each project its own packages

R and Python packages change between versions, and a new version can change a result. If every project on your computer shares one set of packages, updating a package for one project can quietly change another. A project environment avoids this. It is a set of packages that belongs to one project folder, together with a lockfile: a text file that records the exact version of every package.

With an environment and its lockfile, you can come back to an analysis next year, or hand it to a collaborator, and run it with the same packages.

This chapter covers three tools. You do not need all three.

Tool Manages Choose it when
renv R packages Your project uses R.
uv Python and Python packages Your project uses Python.
pixi Python, R, and other software together One environment must hold both languages, or software that is neither.

For each tool, you will learn to create an environment, add packages to it, activate it, deactivate it, and delete it, and how Positron and Quarto find it.

A project with R and Python can simply use renv and uv side by side, each with its own lockfile. This book does that. We do not use conda.

In this chapter, blocks labelled R go in the R console and blocks labelled Bash go in the terminal (see Chapter 1). None of them run when the book is rendered. Work in a new, empty practice folder opened in Positron, not in the book’s folder.

2.2 The five tasks at a glance

NoteOne table to return to
Task renv (R console) uv (terminal) pixi (terminal)
Create renv::init() uv init --bare --python 3.13 pixi init
Add a package renv::install("dplyr"), then renv::snapshot() uv add pandas pixi add pandas
Remove a package renv::remove("dplyr"), then renv::snapshot() uv remove pandas pixi remove pandas
Activate Automatic when R starts in the folder source .venv/bin/activate, or prefix commands with uv run pixi shell, or prefix commands with pixi run
Deactivate renv::deactivate() deactivate exit
Delete installed packages, keeping the lockfile Delete renv/library, then restart R Delete the .venv folder pixi clean
Rebuild from the lockfile renv::restore() uv sync --locked pixi install --locked
Lockfile renv.lock uv.lock pixi.lock

Activate means “use this project’s packages now”. Deactivate means “stop using them”; the environment stays on disk. Delete removes the installed packages. As long as you keep the lockfile, deleting is safe, because the last row rebuilds the environment.

2.3 renv: R packages

NoteCreate

Install renv once per computer, from the R console:

install.packages("renv")

Then open your project folder in Positron and create the environment:

renv::init()

renv adds three things to the folder and restarts R:

File or folder Purpose Share through Git?
renv.lock The lockfile: R’s version and each package’s version. Yes
.Rprofile One line that switches R to the project library when R starts here. Yes
renv/ The project library and renv’s settings. Only activate.R, settings.json, and .gitignore; renv hides the library from Git for you.

renv::init() reads your scripts and .qmd files and installs the packages they use. In an empty folder there is nothing to find, so the lockfile starts with renv alone. To start empty on purpose in a folder that already has code, use renv::init(bare = TRUE).

NoteAdd packages 
renv::install("dplyr")

This installs dplyr into the project library only. The lockfile has not changed yet. Use the package in your code, for example dplyr::filter() in a .qmd file, and then record it:

renv::snapshot()

By default, renv::snapshot() records the packages your project’s files use, and the packages those depend on. A package you installed but never used is left out. This keeps the lockfile to what the analysis needs.

To render Quarto documents that contain R chunks, the project library also needs knitr and rmarkdown. A new renv environment does not have them, and quarto render stops with “The knitr package is not available” until you add them:

renv::install(c("knitr", "rmarkdown"))
renv::snapshot()

Two commands help you keep track:

renv::status()    # Do the library, the lockfile, and your code agree?
renv::remove("dplyr")   # Uninstall a package from the project library.

After removing a package, run renv::snapshot() again so the lockfile matches.

NoteActivate

There is no command to type. When R starts in the project folder, .Rprofile runs and switches R to the project library. In Positron, open the folder and start an R session. The console confirms it:

- Project '~/projects/my-analysis' loaded. [renv 1.2.2]

You can check where R is looking for packages. The first path should be inside your project’s renv/ folder:

.libPaths()

Quarto starts R in the project folder too, so quarto render uses the project library, provided knitr and rmarkdown are installed in it (see “Add packages” above).

NoteDeactivate 
renv::deactivate()

This removes the line from .Rprofile and restarts R, which goes back to your computer’s general package library. renv.lock and the renv/ folder stay where they are. To switch the project library back on:

renv::activate()
NoteDelete, and rebuild

To remove renv from a project completely:

renv::deactivate(clean = TRUE)

This deletes the renv/ folder and renv.lock. Your scripts and data are not touched, but the record of package versions is gone, so use it only when you no longer want the project to use renv.

More often you want a fresh copy of the same environment, for example after a failed installation. Delete the library and keep the lockfile: remove the renv/library folder in Positron’s file explorer, restart R, and run:

renv::restore()

renv::restore() is also the command a collaborator runs after downloading your project. It installs the versions in renv.lock.

renv records R’s version but does not install R. If the lockfile names a different version of R from yours, renv tells you. Some recorded packages may not be compatible with another R version; use the recorded version when reproducing the analysis.

2.4 uv: Python and its packages

NoteCreate

Install uv once per computer by following https://docs.astral.sh/uv/getting-started/installation/, then close and reopen the terminal. Check that it works:

uv --version

In your project folder, create the project file and choose a Python version:

uv init --bare --python 3.13
uv python pin 3.13

uv init --bare writes pyproject.toml, which lists the packages your project asks for, including a Python version requirement. Passing --python 3.13 keeps that requirement consistent with the version we choose. uv python pin writes .python-version. If your computer does not have that version of Python, uv downloads it the first time it is needed. Nothing is installed yet; the environment appears when you run uv sync, uv add, or uv run.

NoteAdd packages 
uv add pandas jupyter

One command does three things: it adds the packages to pyproject.toml, records exact versions in the lockfile uv.lock, and installs them into a new folder named .venv. Add jupyter to any environment that will run Python chunks in Quarto.

uv remove pandas

uv remove reverses all three. Unlike renv, there is no separate snapshot step; the lockfile is updated every time.

File or folder Purpose Share through Git?
pyproject.toml The packages you asked for. Yes
uv.lock The lockfile: every package’s exact version. Yes
.python-version The Python version. Yes
.venv/ The installed packages. No; add .venv/ to .gitignore.
NoteActivate

You have two ways to use the environment from the terminal.

Run one command inside it. Put uv run in front. Nothing needs to be activated, and uv first checks that the environment matches the lockfile:

uv run python script.py
uv run quarto render

Activate it for the whole terminal session. After this, python and quarto use the environment until you deactivate it or close the terminal:

  • macOS and Linux
  • Windows (PowerShell)
source .venv/bin/activate
.\.venv\Scripts\Activate.ps1

The terminal prompt then starts with the environment’s name in parentheses.

In Positron, open the project folder. Positron looks for a .venv folder there and lists it in the interpreter picker; choose it, and the Python console uses the project’s packages. This is separate from the terminal: choosing the interpreter does not activate the environment for commands you type in the terminal.

For Quarto, render with uv run quarto render, or activate the environment first and then run quarto render. Quarto can also discover a project .venv, but an explicit Python setting or Jupyter kernel can affect which interpreter runs. Check the interpreter path if the result is unexpected.

NoteDeactivate

If you activated the environment in a terminal:

deactivate

The prompt loses its prefix, and python means your computer’s Python again. If you only ever used uv run, there is nothing to deactivate.

NoteDelete, and rebuild

The environment is the .venv folder. Delete it in Positron’s file explorer, or from the terminal:

  • macOS and Linux
  • Windows (PowerShell)
rm -rf .venv
Remove-Item -Recurse -Force .venv

Check the folder name before pressing Enter; these commands delete without asking. Rebuild the environment from the lockfile at any time:

uv sync --locked

A collaborator runs the same uv sync --locked after downloading your project. To stop using uv in a project altogether, also delete pyproject.toml, uv.lock, and .python-version.

2.5 pixi: one environment for Python, R, and more

NoteWhat pixi is, and when to prefer it

pixi builds a single environment that can contain Python, R, their packages, and other software such as command-line tools. Choose it when an analysis needs both languages to share one environment, or needs software that renv and uv cannot install.

pixi installs packages from conda-forge, the community collection that conda also draws on, but it is a separate program and you do not install conda. This has two consequences worth knowing. R packages have an r- prefix, so dplyr is r-dplyr. And conda-forge can lag behind: R itself and some R packages arrive there later than on CRAN, and a few are not there at all.

Use renv or pixi for a project’s R packages, not both.

NoteCreate

Install pixi once per computer by following https://pixi.sh/latest/installation/, then close and reopen the terminal. In your project folder:

pixi init

This writes pixi.toml, which lists what the project asks for, and a .gitignore entry that keeps the installed packages out of Git. As with uv, the environment itself appears when you add the first package.

NoteAdd packages 
pixi add python=3.13 pandas jupyter
pixi add r-base r-dplyr r-knitr r-rmarkdown

python and r-base are the languages themselves. jupyter lets Quarto run Python chunks; r-knitr and r-rmarkdown let it run R chunks. Each pixi add updates pixi.toml, records exact versions in the lockfile pixi.lock, and installs into a hidden .pixi folder.

pixi remove pandas
File or folder Purpose Share through Git?
pixi.toml The software you asked for. Yes
pixi.lock The lockfile: every package’s exact version. Yes
.pixi/ The installed software. No; pixi init adds it to .gitignore.
NoteActivate

The choices mirror uv’s.

Run one command inside the environment:

pixi run python script.py
pixi run Rscript analysis.R
pixi run quarto render

Activate it for the terminal session:

pixi shell

pixi shell starts a new shell inside the current terminal with the environment switched on. The command is the same on macOS, Linux, and Windows.

In Positron, open the project folder. Positron lists a pixi environment’s Python in the interpreter picker. Finding R inside a pixi environment is an experimental Positron feature: switch on the setting positron.r.interpreters.pixiDiscovery, and expect that some R features may not work as they do with an ordinary R installation.

For Quarto, render with pixi run quarto render.

NoteDeactivate

Leave the shell that pixi shell started:

exit

You are back in your ordinary terminal. If you only used pixi run, there is nothing to deactivate.

NoteDelete, and rebuild 
pixi clean

pixi clean removes the installed environment from the .pixi folder and keeps pixi.toml and pixi.lock. Rebuild it with:

pixi install --locked

To stop using pixi in a project altogether, also delete pixi.toml, pixi.lock, and the .pixi folder.

2.6 Check that Quarto uses your environment

NoteAsk the code where it is running

A rendered document can report which R or Python ran it. Put the chunk for your language in a .qmd file in the practice folder and render it.

```{r}
R.version.string
.libPaths()[1]
```

```{python}
import sys
print(sys.version)
print(sys.prefix)
```

With renv, the library path should be inside the project’s renv/ folder. With uv, sys.prefix should end in .venv. With pixi, it should end in .pixi/envs/default.

For R inside a pixi environment, check R.home() instead, which should be inside the .pixi folder. .libPaths() can list a personal library first if your computer also has an ordinary installation of the same R version, so pixi’s R is less sealed off from the rest of your computer than a renv project is.

If an R chunk fails with “The knitr package is not available”, install knitr and rmarkdown into the environment, as shown in the renv and pixi sections.

If a Python chunk fails, or reports a Python from somewhere else on your computer, work through this list:

  1. Did you render with uv run quarto render or pixi run quarto render, or activate the environment first?
  2. Is jupyter installed in the environment? Quarto needs it to run Python chunks.
  3. Does your computer have Jupyter kernels left over from other projects? Run uv run jupyter kernelspec list (or pixi run jupyter kernelspec list) to inspect them. The name python3 does not by itself prove a kernel belongs to this project. For a Python-only document, select the Python kernel:
---
title: "My analysis"
jupyter: python3
---

Run uv run quarto check jupyter or pixi run quarto check jupyter to inspect the Python environment Quarto sees, and verify sys.prefix in the rendered document. A document containing both R and Python chunks normally uses knitr and reticulate instead; see Quarto’s Python guide.

2.7 This book’s environments

NoteRestore, do not create

The book’s folder already contains its environments, so you restore them and do not create new ones. Open the folder in Positron. For R, which every current chapter uses, run this in the R console and agree when renv asks whether to install:

renv::restore()

For Python, which no current chapter needs yet, run this in the terminal:

uv sync --locked

--locked tells uv to stop with an error if uv.lock is out of date, so it cannot change the lockfile behind your back.

2.8 Good habits

NoteSmall rules that prevent large problems
  1. One environment per project folder. Do not share an environment between projects, and do not install a project’s packages into your computer’s general library.
  2. Commit the lockfile; ignore the installed packages. renv.lock, uv.lock, and pixi.lock belong in Git. renv/library, .venv, and .pixi do not.
  3. Add packages with the tool. Inside a uv project, use uv add, not pip install. Inside a pixi project, use pixi add. Otherwise the lockfile no longer describes what is installed.
  4. Record after you change. With renv, run renv::snapshot() after adding or removing a package, and renv::status() when unsure.
  5. Report your versions. When you write up results, state the versions of R or Python and of the main packages. The lockfile has them.

2.9 Practice

NoteTry it in a practice folder
  1. Create an empty folder, open it in Positron, and set up renv. Install jsonlite, use it in a short .R file, and snapshot. Which line of renv.lock names jsonlite’s version?
  2. In the same folder, create a uv environment with pandas. Run uv run python -c "import pandas; print(pandas.__version__)". Then delete .venv and run the command again. What happens, and why?
  3. A classmate sends you a project containing renv.lock, pyproject.toml, and uv.lock, with no renv/library or .venv folder. Which two commands set up both environments?
  4. You ran renv::install("survey") and then renv::snapshot(), but renv.lock does not list survey. Name the likely reason.
  5. Why does this book tell you to delete .venv freely but to think before running renv::deactivate(clean = TRUE)?
TipSuggested answers

1. renv.lock has a "jsonlite" entry under "Packages", and its "Version" line holds the version.

2. The command works both times. uv run notices that the environment is missing and rebuilds it from uv.lock before running Python. The lockfile, not the .venv folder, is the record of the environment.

3. renv::restore() in the R console, and uv sync in the terminal.

4. No file in the project uses survey yet. The default snapshot records the packages your code uses, so an installed but unused package is left out. Call the package in a script or .qmd file, for example survey::svydesign(), and snapshot again.

5. .venv holds only installed packages, which uv sync rebuilds from uv.lock. renv::deactivate(clean = TRUE) deletes renv.lock as well, and without the lockfile the exact versions cannot be rebuilt.
